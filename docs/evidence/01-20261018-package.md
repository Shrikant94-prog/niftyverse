## Investigation and limits

The original wheel helper wrongly assumed metadata specifier order and uv
dry-run target absence; inspection showed canonical `<3.15,>=3.14` and a target
containing only uv's `.lock`. A subsequent 3.15 dry-run unexpectedly succeeded.
Bounded re-investigation of installed help and [uv compatibility documentation](https://docs.astral.sh/uv/pip/compatibility/)
confirmed uv pip deliberately ignores upper Python bounds. The helper now uses
pip 26.2.1 to exercise rejection. This is a resolver limitation, not permission
to change the package pin or claim uv pip enforces the upper bound.

Candidate names, versions and metadata were read from the official PyPI JSON
API and checked by actual installs; public references are
[yfinance](https://pypi.org/project/yfinance/1.7.0/),
[Arelle](https://pypi.org/project/arelle-release/2.46.1/) and
[py-xbrl](https://pypi.org/project/py-xbrl/3.0.3/).
Their import compatibility establishes no parsing/source-data support.

The installed smoke child installs its Python audit hook before package import,
denies socket operations and child-process launches, and exercises an actual
socket negative control in that same subprocess. Installation/build acquisition
is outside this offline boundary. This is not OS firewall/native-library network
isolation; no live provider calls or taxonomy resolution were exercised.
Linux/macOS and hosted CI results remain unobserved. Owner display review is
separate and must use the forthcoming actual slice previews.
